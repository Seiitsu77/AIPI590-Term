# Anime Compass 冷启动层：用另类数据给新番排序

> **状态：想法验证阶段。** 第一轮可行性实验已经跑完。事先定好的检验没有通过，但过程中发现了一个测量缺陷。修正之后，开播前的信号真实但偏弱；开播后第一周的信号在非线性模型下明显更强，还需要在新数据上确认。下面把想法、已经做的事和目前的结论都写清楚。

## 一句话

新番刚上线时没有评分，协同过滤推荐不了它。这个项目想验证：开播前的外部关注度数据（比如 Wikipedia 浏览量）能不能让推荐系统在第一天就判断一部新番值不值得推、该推给谁。

这也是我 Duke AIPI 590（Alternative Data）term project 的候选方向。

## 背景：Anime Compass 是什么

Anime Compass 是我之前做的个性化动画推荐系统。你选几部喜欢的番，它在约 18,000 部的全量片库里给你排序。

- 代码：<https://github.com/Seiitsu77/anime-compass>
- Demo：<https://anime-compass-xijwv9hjuqvoskonhrwtus.streamlit.app/>

已经做完的部分：

- **数据**：MAL 的 5,763 万条历史评分，其中 3,088 万条正反馈（评分 8 分及以上）用于训练。
- **模型**：implicit ALS 召回 top-300，再用 LambdaMART 重排。
- **效果**：在同一组 800 个留出用户上做全片库排序，ALS 的 NDCG@10 是 0.2588，之前的十通道 hybrid 是 0.1815；延迟从 924.6 ms 降到 2.0 ms。在另一组 800 个用户上，重排把 NDCG@10 从 0.2456 提到 0.2828。
- **做法**：每个模型决策都有对照实验，判定规则在看结果之前写好。被否决的方案也都留了记录，包括预训练文本 embedding、learned fusion、按用户活跃度分流、LightFM。
- **工程**：449 个测试，产物带校验和，线上路径只依赖 NumPy。

## 它解决不了的问题

ALS 只能给有交互记录的番打分。具体有三个限制：

1. **新番进不了候选池。** ALS 推荐出去的番 100% 落在最热门的 20% 里，中尾和长尾的曝光是 0。一部刚开播的番没有任何评分，所以永远不会被召回。
2. **重排帮不上忙。** 重排模型只对 ALS 的 top-300 重新排序，新番不在里面。
3. **数据停在 2021 年初。** 片库和评分都是那时的快照，2021 年以后的番对系统来说全部是冷启动。

## 想法

把冷启动拆成两个问题，分别用不同的数据回答：

| 问题 | 用什么回答 | 例子 |
|---|---|---|
| 推给谁 | metadata：系列、工作室、原作类型、题材 | 喜欢前作的人会想看续集 |
| 值不值得推 | 另类数据：开播前的外部关注度 | 一部没有前作的原创番，词条浏览量突然上升 |

我认为另类数据真正有用的地方是第二行的例子。热门续集大家本来就知道，metadata 也看得出来；没有前作、没有名厂背书的黑马，只有外部关注度能提前看到。

产品形态上，我打算做成 Anime Compass 里单独的一栏"新番 · 为你推荐"，不混进主推荐列表。原因是主列表里每加一路召回源，NDCG@10 都会掉（之前试过 item-item 补充，掉了 9%），而且两种来源的分数不可比。

可能的使用者有两类。一类是粉丝：每季四五十部新番，现有的新番导视都按人气排序，没有个性化。另一类是平台：买版权和排推广位是在开播前决定的，那时平台自己还没有任何观看数据。

## 第一轮可行性实验

实验只回答一个窄问题：**开播前的 Wikipedia 浏览量，在 metadata 已经知道的东西之外，还能不能多预测一点？**

这轮只测了"值不值得推"这一半，也就是预测一部番最终有多少人喜欢。"推给谁"这一半还没测。

### 数据

| 来源 | 内容 |
|---|---|
| MAL 片库快照（Kaggle，CC0） | 2016–2020 年首播、有完整日期的动画 3,534 部，其中 TV 动画 1,183 部 |
| Wikidata | 用"MyAnimeList anime ID"属性把番映射到英文、日文、中文 Wikipedia 词条 |
| Wikimedia Pageviews API | 3,168 篇词条 2015-07 到 2021-03 的每日浏览量 |

队列从 2016 年开始，是因为 Wikipedia 的浏览量数据从 2015 年 7 月才有。浏览量是按天记录、不回填的，所以"开播前 30 天的浏览量"是严格的当时数据。

### 方法

所有定义都在看结果之前写进了 `src/analyze.py`：

- **预测目标**：这部番最终有多少 MAL 用户打了 8 分及以上（取对数）。这和 Anime Compass 训练 ALS 用的正反馈定义一致。
- **基线**：只用开播前就知道的 metadata，包括类型、原作、分级、题材、集数、首播季度、工作室历史表现、系列前作人气。
- **另类数据特征**：三种语言各自在开播前 30 天和前 31–90 天的浏览量。
- **切分**：用 2016–2018 年首播的番训练，在 2019–2020 年首播的番上测试。按时间切，不随机切。
- **指标**：在每一季内部算预测排名和真实排名的 Spearman 相关，再取平均。新番栏只需要把同一季的番排对。
- **判定规则**：加上浏览量之后的提升为正，并且 95% bootstrap 区间的下界大于 0，才算通过。

### 结果：没有通过

主样本是有 Wikipedia 词条的 TV 动画，训练 517 部，测试 275 部。

| 信息集 | 季内 Spearman |
|---|---:|
| 仅 metadata | 0.731 |
| metadata + 开播前浏览量 | 0.735 |

提升是 +0.004，95% 区间 [−0.019, +0.027]，包含 0。按事先定的规则，这是 FAIL。

### 事后发现的测量缺陷

看完结果之后我去检查了数据，发现最热门的五分之一里，215 部有词条的番中有 36 部在三种语言下的开播前浏览量都是 0。其中包括《我的英雄学院》《鬼灭之刃》《Re:Zero》《为美好的世界献上祝福》《辉夜大小姐想让我告白》。

这些番不可能没人搜。问题出在实体映射上：它们被映射到了"season 1"和"(TV series)"这类词条，而这类词条是开播几年之后才从主词条里拆出来的，开播前根本不存在。开播前的关注度都在主词条（通常是漫画词条）上，我的映射规则少往上走了一步。

下图是按预设映射画的，左边那一列就是被错记成 0 的番：

![开播前浏览量与最终受众，预设映射](figures/fig2_preair_views_vs_audience.png)

也就是说，这个检验恰好在信号应该最强的那批番上看不到信号。

### 修正映射后的探索性结果

我把一部番的关注度改成它自己的词条、系列词条和原作词条三者之和，然后把同一套分析原样重跑了一遍。样本、切分、特征、模型、指标都没有变。

**这部分是看过结果之后做的，属于探索性分析，不能改变上面的 FAIL。**

| | 预设映射 | 修正映射 |
|---|---:|---:|
| 热门番里浏览量被记成 0 的数量 | 36 | 1 |
| 只用浏览量的季内 Spearman | 0.251 | 0.565 |
| 加到 metadata 上的提升（ridge） | +0.004 [−0.019, +0.027] | +0.021 [−0.007, +0.048] |
| 提升（boosted trees） | +0.055 [−0.004, +0.114] | +0.054 [−0.008, +0.119] |
| 只看新作的提升（ridge） | +0.013 [−0.025, +0.053] | +0.032 [−0.012, +0.079] |

把 2018、2019、2020 三年分别单独作为测试年，提升都是正的（+0.025、+0.016、+0.035），但每一个的区间都包含 0。

最终受众最多的三分之一和最少的三分之一，在开播前 90 天的关注度就已经拉开了：

![首播前后的关注度曲线，探索性映射](figures/exploratory_fig5_attention_around_premiere.png)

### 第二个探索性分析：开播后第一周

开播前的数据只能量"期待"，量不了"口碑"。所以我换了一个问题：开播一周后，这部番仍然几乎没有评分，协同过滤还是用不了，但第一集已经播了，这一周有多少人去查它是知道的。对第 7 天做的决策来说，用第 0 到第 6 天的浏览量不算偷看未来。

**这同样是看过前面的结果之后做的探索性分析。**

在 metadata 和开播前浏览量的基础上，再加上开播后前 N 天的浏览量：

| 累计信息 | Ridge | Boosted trees |
|---|---:|---:|
| 仅 metadata | 0.731 | 0.733 |
| + 开播前浏览量 | 0.752 | 0.786 |
| + 开播后前 3 天 | 0.746 | 0.819 |
| + 开播后前 7 天 | 0.756 | 0.846 |
| + 开播后前 14 天 | 0.760 | 0.861 |
| + 开播后前 28 天 | 0.758 | 0.870 |

第 7 天相对仅 metadata 的提升：ridge 是 +0.025 [−0.008, +0.059]，boosted trees 是 +0.113 [+0.048, +0.182]。把 2018、2019、2020 分别单独作为测试年，boosted trees 的提升是 +0.098、+0.135、+0.102，三个区间都不包含 0。

两个模型的结论不一致。线性模型看不到稳定的提升，非线性模型在每个时间点都看到了，而且观察的天数越多提升越大。我把两个都列出来，因为事后挑一个模型就等于挑答案。

![观察天数与排序质量，探索性分析](figures/exploratory_fig6_information_by_day.png)

## 目前的判断

1. **浏览量是真信号。** 修正映射之后，只靠开播前浏览量就能把一季新番排到 0.565。
2. **开播前，它和 metadata 重合得很厉害。** 系列前作人气和工作室历史表现已经能排到 0.731，开播前浏览量在这之上只多出 0.02 到 0.05，统计上还没有站住。
3. **开播后第一周可能才是另类数据真正有用的时间点。** 用非线性模型，第 7 天能排到 0.846，三个测试年都一致。但线性模型不支持这个结论，而且这是探索性分析，需要在新数据上确认。
4. **冷启动这个功能本身是可行的。** 只用 metadata 先验就有 0.731，新番栏不依赖外部数据也能做。另类数据是在这个基础上的加分项。
5. **实体映射是这类数据最容易出错的地方。** 映射率看起来有 67%，但错的恰好是最重要的那批番。

## 这个实验的局限

- **覆盖率偏向热门番。** 最冷门的五分之一只有 7% 有开播前浏览量。一部番今天有没有词条，本身就和它后来红不红有关。
- **目标只代表 MAL 社区。** MAL 用户偏英语区的核心向观众。
- **基线偏强。** 工作室和系列先验用的是 2021 年快照里的数字，不是开播当时的数字，这对基线有利。
- **续集靠标题匹配识别。** 片库里没有系列字段，会有漏判和误判。
- **MAL 自己的数据没法比。** 快照没有时间维度，开播前的"想看"数和开播后第一周的成员数都还原不出来。这是最强的站内基线，目前缺席。
- **同一个测试集已经看过好几次。** 两个探索性分析都是在它上面做的，结论需要新数据确认。
- **只试了一个数据源。**

## 下一步

1. **做一次干净的样本外检验**：拿 2021 年以后首播的番做新队列，用修正后的映射，把规则预先提交到 git 再跑。开播前和开播后第一周两个问题都要重新检验。
2. **补上 MAL 自己的基线**：从 Wayback Machine 的历史快照里还原开播前后的成员数，看 Wikipedia 在它之上还有没有增量。
3. **再考虑别的数据源**：B 站、YouTube、MAL 都只公开当前数值，过去的番没法回测，只能从现在开始逐日采集。Google Trends 有历史，但它和 Wikipedia 量的是同一个东西，三种语言的 Wikipedia 叠在一起也没有比单个更好。
4. **测"推给谁"**：用 metadata 给新番合成一个 ALS 向量，看它能不能被推给真正喜欢它的用户。
5. **把新番栏接进 Anime Compass**：先只用 metadata 先验做出原型。

## 还没想清楚的问题

- 线性模型和非线性模型结论不一致，该信哪个？我的猜测是浏览量为 0 的番在线性模型里被当成了"极冷门"，而实际上是"没量到"，但这个猜测还没验证。
- 把问题从"开播前"改成"开播后第一周"，还算不算冷启动？
- 有没有比 Wikipedia 更好的信号，并且拿得到历史数据？
- 预测"多少人打 8 分以上"是合适的目标吗？它偏向大众向的番，可能和"适合这个用户"不是一回事。
- 和 MAL、B 站相比，中立和跨平台算不算真正的优势？这部分的竞品信息我还没有逐条查证。

## 复现

需要 Python 3.10 和 pandas、numpy、scipy、scikit-learn、matplotlib、requests。`data/raw/anime.csv` 来自 [Anime Recommendation Database 2020](https://www.kaggle.com/datasets/hernan4444/anime-recommendation-database-2020)（CC0）。

预设分析：

```bash
python src/build_cohort.py && python src/map_wikipedia.py && python src/fetch_pageviews.py && python src/analyze.py && python src/figures.py
```

探索性分析和报告：

```bash
cd src && python map_wikipedia_exploratory.py && cd .. && python src/fetch_pageviews.py && python src/analyze.py --exploratory && cd src && python analyze_after_premiere.py && cd .. && python src/figures.py --exploratory && python src/report.py
```

抓取浏览量前可以设置环境变量 `WIKIMEDIA_CONTACT`（一个邮箱或网址）。设了大约半小时抓完；不设的话 Wikimedia 对匿名客户端限速，需要五小时左右。
